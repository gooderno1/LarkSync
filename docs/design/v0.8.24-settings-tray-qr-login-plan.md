# LarkSync v0.8.24 设置、自启动、托盘菜单与扫码登录方案

## 1. 本轮目标

- 将“开机自启动”从仅托盘可见的隐藏能力提升为设置页中的设备级设置。
- 重构托盘右键菜单的信息架构，只保留真实可执行、可验证的动作。
- 明确当前二维码为什么只能展示、不能稳定完成手机扫码登录，并给出可落地的跨设备授权方案。

## 2. 当前问题

### 2.1 开机自启动

- Windows 已通过用户 Startup 目录中的 `LarkSync.lnk` 实现。
- macOS 已通过 `~/Library/LaunchAgents/com.larksync.agent.plist` 实现。
- 当前入口只在托盘右键菜单，设置页无法查看真实状态，也无法启停。
- 自启动是操作系统状态，不属于普通配置文件字段；设置页应直接读写系统状态，不随“保存设置”批量提交。

### 2.2 托盘菜单

- `pystray` 使用操作系统原生菜单，不能复用 React/Tailwind 的颜色、圆角、阴影和卡片样式。
- 当前菜单层级过平，包含“打开桌面窗口”和“在浏览器中打开”等同级低频入口。
- “暂停同步”目前只改变托盘自身的图标状态，不会暂停后端调度器、Watcher 或正在执行的同步，属于误导性功能。
- 自启动状态通过文本前缀 `✓` 和空格模拟，视觉不稳定；应使用原生 `checked` 状态。

## 3. 设置页设计

### 3.1 位置

在“飞书账号与当前设备”卡片的“当前设备”分区增加“启动与后台”行：

- 标题：`开机自启动`
- 说明：`登录当前系统账号后自动启动 LarkSync，并在托盘或菜单栏保持同步。`
- 控件：与当前浅色页面一致的蓝色 Switch。
- 状态：加载中、已开启、已关闭、不支持、操作失败。

### 3.2 交互

- 页面进入时调用 `GET /system/autostart`。
- 用户切换时调用 `PUT /system/autostart`，请求体为 `{ "enabled": true | false }`。
- 操作成功后使用服务端返回的真实状态更新界面。
- 操作失败时回滚 Switch，并展示 Toast；不得仅按用户点击结果乐观显示成功。
- Linux 或无桌面环境返回 `supported=false`，控件禁用并显示“不支持当前平台”。

### 3.3 API 契约

```json
{
  "supported": true,
  "enabled": true,
  "platform": "windows"
}
```

- Windows：创建、校验或删除 Startup 快捷方式。
- macOS：创建、加载、校验或移除 LaunchAgent。
- API 调用放入工作线程，避免 PowerShell、COM 或 `launchctl` 阻塞 FastAPI 事件循环。

## 4. 托盘菜单重构

### 4.1 视觉策略

不引入自绘托盘弹窗。本轮继续使用原生菜单，以获得稳定的焦点、DPI、键盘、屏幕边缘定位和跨平台行为；通过文案、层级、原生勾选态和页面一致的命名改善体验。

### 4.2 新信息架构

```text
LarkSync · 空闲                         （只读状态）
────────────────────────
打开 LarkSync                          （默认动作）
立即同步
────────────────────────
活动与问题
设置
更多  ›
  在浏览器中打开
  开机自启动                           （原生勾选态）
────────────────────────
退出 LarkSync
```

### 4.3 功能取舍

- 保留：打开桌面端、立即同步、活动与问题、设置、浏览器备用入口、开机自启动、退出。
- 移除：当前不真正暂停后端的“暂停同步”。
- “立即同步”继续只触发已启用任务。
- 自启动菜单与设置页共享同一底层状态；切换失败时通知必须显示失败，不能把失败误报成“已禁用”。

## 5. 真正扫码登录的可行性

### 5.1 当前方案为什么失败

当前二维码只是把标准 OAuth 授权 URL 编码成图片。默认 `redirect_uri` 为本机 `localhost`。手机扫码后，飞书授权页运行在手机上，授权完成时手机访问的是手机自己的 `localhost`，桌面端收不到授权码。

### 5.2 官方能力边界

- 飞书公开 OAuth 支持授权码、`state`、`redirect_uri`、PKCE `code_challenge/code_verifier`。
- 授权码有效期为 5 分钟且只能使用一次。
- 当前公开认证文档未列出可供普通自建应用直接调用的标准 Device Authorization Grant 端点。
- `lark-cli auth login` 虽提供设备流，但其凭据由 CLI 自己管理；LarkSync 现有直连 OpenAPI 客户端无法安全取得并复用该 Token，因此不能把 CLI 辅助状态直接当作产品登录闭环。

### 5.3 推荐方案：一次性 HTTPS 回调中继 + PKCE

新增一个最小化公网授权中继，只转交一次性授权码，不保存 App Secret、access token、refresh token 或用户云文档数据。

```text
桌面端创建一次性会话与 PKCE
        ↓
二维码包含飞书 OAuth URL
redirect_uri 指向固定 HTTPS 中继
        ↓
手机飞书扫码并确认授权
        ↓
飞书将 code + state 回调到中继
        ↓
桌面端凭高熵轮询密钥取回一次性 code
        ↓
桌面端用 code_verifier 在飞书 v3 Token 端点换取 Token
        ↓
Token 只写入本机 DPAPI / Keychain
```

### 5.4 安全约束

- 桌面端生成 `state`、`poll_secret`、`code_verifier`；二维码中不得包含 `poll_secret` 或 `code_verifier`。
- 使用 PKCE S256；即使中继中的授权码泄露，没有本机 `code_verifier` 也不能换取 Token。
- 中继中的 code 最长保留 5 分钟，读取一次后立即删除。
- 中继只保存会话散列、状态、过期时间和加密后的 code；日志禁止记录 code。
- 桌面端校验 `state`、会话状态和过期时间。
- Token 交换和 Token 刷新仍在本机完成；App Secret 与 Token 不上传中继。
- 需要在飞书开发者后台新增固定 HTTPS 回调 URL。

### 5.5 建议实施阶段

1. 原型：实现本地会话状态机和假的中继适配器，覆盖创建、等待、成功、拒绝、过期和重复消费测试。
2. 中继：使用最小无状态 HTTP 服务加短期存储，加入速率限制、一次性读取和审计脱敏。
3. 桌面端：新增 `/auth/qr/sessions`、`/auth/qr/sessions/{id}`、`/auth/qr/sessions/{id}/cancel`，前端展示真实状态而不是静态二维码。
4. Token：将现有 AuthService 切换到 OAuth v3 Token 端点并加入 PKCE verifier。
5. 验收：两台网络不同的设备完成手机扫码、桌面自动登录；同时覆盖拒绝授权、手机断网、中继超时、code 重放和 state 不匹配。

## 6. 本轮交付边界

- 本轮实现设置页自启动控制和托盘菜单重构。
- 本轮移除托盘中的假暂停入口，不扩展全局暂停状态机。
- 本轮只形成扫码登录的可实施方案，不新增公网中继或改变现有 OAuth 生产链路。
