## 2. 正式版证据与根因

### 2.1 失败运行加载慢

正式库大小约 `2.23 GB`，`sync_run_events` 共约 `2,605,791` 条。

同一任务的运行事件接口实测：

- 有 2,929 条事件的最近成功运行：约 `14–151 ms`。
- 只有 4 条事件的失败运行：约 `1,640–1,744 ms`。
- 只有 3 条事件的较早成功运行：约 `1,727 ms`。

因此，慢的不是“失败解析”，而是“小型、较早运行”的查询路径。

页面当前同时传入：

- `task_ids=<task_id>`
- `run_ids=<run_id>`

SQLite 因此选择 `idx_sync_run_events_task_timestamp`，先扫描该任务的大量历史，再过滤运行 ID。运行越早、事件越少，反而越慢。

运行 ID 是系统生成的全局 UUID。活动页面已经从任务诊断接口取得可信运行 ID，因此事件明细查询只需传运行 ID，直接命中现有 `idx_sync_run_events_run_timestamp`，不需要新增大型索引，也不会增加升级迁移时间。

### 2.2 大量“等待上传”

正式库中 `queued` 事件约 `836,263` 条，其中单个大任务约 `605,019` 条。

最近一次大运行包含：

- `skipped`：1,463 条，说明“云端未更新，跳过下载”。
- `queued`：1,460 条，说明“等待周期上传”。
- 两类记录的路径和时间一一接近。

根因：

1. 下载检查读取本地文件并计算哈希。
2. Watchdog 会产生 `opened`、`closed`、`closed_no_write` 等只读事件。
3. 当前 `FileEventHandler.on_any_event()` 未筛选事件种类。
4. 只读打开/关闭也进入 `_handle_local_event()`。
5. 路径被加入上传内存队列，并持久化一条“等待周期上传”。

这不是 83 万个文件真的需要上传，而是只读访问被误识别为修改。

### 2.3 问题中心“打开文件夹”无效

任务详情接口会先把路径转换为 `Path`，问题动作却直接把字符串传给 `open_directory_in_file_manager()`。

该函数第一步调用 `path.expanduser()`，字符串没有此方法，因此动作失败。

### 2.4 页面比例与详情形态

- 设置和维护页面目前占满所有可用宽度；最大化后卡片横向拉长，内容列与辅助列比例失衡。
- 更新检查按钮位于整个维护页标题右侧，但它只属于“更新流程”，与日志保留、重置映射无直接关系。
- 事件详情在标准/宽屏模式使用右侧 400px 覆盖抽屉，只覆盖事件区，任务和运行仍占宽度，详情阅读区域狭窄。

## 3. 页面布局设计

### 3.1 设置页面

- 页面内容使用 `width: 100%`、`max-width: 1240px`、水平居中。
- 最大化时保留左右呼吸区，不继续拉伸表单和说明文本。
- 账号/设备上下文继续保持约 `41% / 59%`，但只在 1240px 内容宽度内计算。
- 现有保存入口、面板顺序和数据逻辑不变。

### 3.2 更新与维护页面

- 页面内容同样限制为 `max-width: 1240px` 并居中，与设置页形成统一阅读宽度。
- 主工作区调整为：
  - 更新主区：弹性宽度。
  - 维护侧栏：`340px`。
- “检查更新”从页面总标题右上角移入“更新流程”标题行。
- 更新流程标题行同时显示说明和检查按钮；按钮与当前版本、下载、安装操作形成同一任务上下文。
- 页面总标题只承担导航与范围说明，不放局部动作。
- 检查按钮保持唯一，不在其他位置重复。

## 4. 活动运行查询设计

### 4.1 请求规则

- 已选择运行 ID 时：
  - 只发送 `run_ids=<run_id>`。
  - 不再同时发送 `task_ids`。
- 尚未选择运行 ID、仅按任务浏览时：
  - 继续发送 `task_ids=<task_id>`。

运行 ID 来自所选任务诊断响应，不由用户自由输入。该调整复用现有运行 ID 索引，不新增数据库迁移。

### 4.2 验收样例

- 输入：任务 A + 失败运行 R。
- 旧请求：`task_ids=A&run_ids=R`。
- 新请求：`run_ids=R`。
- 预期：
  - 返回内容与总数不变。
  - 查询计划使用运行 ID 索引。
  - 正式大库同类 3–4 条事件运行不再等待约 1.7 秒。

## 5. 等待上传语义与监听规则

### 5.1 Watchdog 事件白名单

仅以下文件系统事件进入同步：

- `created`
- `modified`
- `moved`
- `deleted`

以下只读或生命周期事件忽略：

- `opened`
- `closed`
- `closed_no_write`
- 其他未知事件

目录删除仍按现有删除联动处理；普通目录创建、修改和移动仍由现有业务规则决定是否处理。

### 5.2 上传队列与活动记录分离

- 真实文件变更仍加入内存上传队列，等待静默窗口后执行。
- “等待周期上传”只表示瞬时调度状态，不再写入持久化活动历史。
- 上传真正执行后，继续记录：
  - 上传成功。
  - 内容未变/规则跳过。
  - 上传失败。
  - 冲突或删除结果。
- 历史 `queued` 事件不删除，保留审计和兼容性。

### 5.3 活动筛选

- 默认筛选从“全部事件”调整为“处理结果”。
- “处理结果”包含开始、完成、上传、下载、删除、跳过、失败、中断与冲突，但排除历史 `queued`。
- 保留“全部事件”入口，用户需要时仍可查看旧版排队记录。
- 增加“历史排队”筛选，明确这些记录是旧版调度检测，不代表仍有待执行任务。

## 6. 问题中心打开目录

- 问题动作执行前将任务本地路径转换为 `Path`。
- 目录不存在返回明确错误，不记录伪成功。
- 动作成功后前端提示“已打开本地目录”，不显示“等待验证”。
- 打开目录仍写问题动作审计，但不改变问题解决状态。

## 7. 事件详情交互

### 7.1 标准与宽屏

采用居中模态框：

- 遮罩覆盖活动页面内容。
- 最大宽度 `720px`。
- 最大高度为视口高度减 80px。
- 头部、正文、底部动作分区；正文独立滚动。
- 点击遮罩、关闭按钮或按 `Escape` 关闭。
- 使用 `role="dialog"`、`aria-modal="true"` 和标题关联。
- 关闭后任务、运行、筛选、分页和滚动上下文不变。

不再使用覆盖事件区的 400px 右侧抽屉。

### 7.2 紧凑模式

- 保持整页详情。
- 使用明确的“返回事件列表”入口。
- 不叠加居中弹窗，避免窄窗口双层滚动。

## 8. 测试计划

### 8.1 后端

- `opened`、`closed`、`closed_no_write` 不触发同步回调。
- `created`、`modified`、`moved`、`deleted` 继续触发。
- 本地真实修改加入内存队列，但不持久化 `queued` 活动事件。
- 问题动作使用 `Path` 打开任务目录。
- 目录打开失败返回明确错误并写失败动作。

### 8.2 前端

- 有运行 ID时事件请求不包含 `task_ids`。
- 无运行 ID时仍使用任务过滤。
- 默认事件筛选为“处理结果”。
- “全部事件”和“历史排队”仍可选择。
- 设置与维护页包含统一最大内容宽度。
- 检查更新按钮只出现一次，并位于更新流程区域。
- 标准/宽屏事件详情使用居中 dialog，不再包含右侧 400px 抽屉样式。
- 紧凑模式继续使用整页详情。

### 8.3 全量验证

- 后端 pytest。
- 前端 TypeScript、ESLint、Vitest、Vite build。
- Windows NSIS 正式安装包构建。
- GitHub Actions 三平台构建与安装启动 smoke。

## 9. 历史兼容与非目标

- 不删除 83.6 万条历史 `queued` 证据。
- 不执行启动期大表重写或新增大型索引。
- 不改变飞书 API、同步方向和冲突策略。
- 不操作用户正式数据库、同步目录或云端文件。
- 本版重点是阻止新噪音继续产生、默认隐藏旧瞬时队列，并恢复运行查询和页面交互的合理性。
