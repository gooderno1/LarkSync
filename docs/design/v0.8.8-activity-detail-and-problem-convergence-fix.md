# LarkSync v0.8.8 活动详情与历史问题收敛修复

## 1. 正式版只读审计结论

### 1.1 活动详情“点了没内容”

- 正式库包含 `2,596,632` 条 `sync_run_events`。
- `/sync/logs/sync` 同时执行总数查询和分页查询。
- 按运行筛选时使用 `coalesce(run_id, '') IN (...)`，SQLite 无法执行索引等值查找。
- 当前条件的总数查询会扫描完整 `run_id` 索引；分页查询会扫描时间索引后再排序。
- 同一正式库只读对比：
  - `coalesce(run_id, '')` 总数查询约 `186.6ms`，直接 `run_id IN (...)` 约 `0.1ms`。
  - `coalesce(run_id, '')` 首页查询约 `1332.7ms`，直接 `run_id IN (...)` 约 `0.5ms`。
- 应用运行中存在同步写入竞争时，正式日志记录到该接口耗时 `5.865s` 至 `16.287s`；前端在等待期间表现为详情空白。

### 1.2 重复“待删”与空活动

- 最近七天有 `777` 次含 `delete_pending` 的运行。
- 这些运行累计记录 `1,281` 条 `delete_pending`，但没有产生对应删除结果。
- 历史墓碑中有 `1,728` 条 cloud 来源记录最终被取消，原因均为“云端文件已恢复”。
- 当前下载流程先用目标路径集合判定“云端缺失”，建立待删墓碑并记录活动；同一轮稍后又用稳定 cloud token 确认对象存在并取消墓碑。
- `create_or_refresh()` 只复用 pending 墓碑；取消记录在下一轮不能复用，因此同一对象反复执行“新建待删 → token 确认存在 → 取消”。
- 这是路径映射与 token 验证先后顺序造成的逻辑竞争，不是用户真实删除。

### 1.3 问题中心仍有 2000 条错误

- 当前未解决问题共 `2,010` 条：
  - upload：`1,909`
  - system：`85`
  - auth_permission：`15`
  - local_io：`1`
- 其中 `1,988` 条最后出现时间超过 30 天；最近 7 天只有 `6` 条。
- 精确 `resolution_key` 与更晚 `problem_recovery_facts` 匹配数为 `0`，说明后台消费游标正常，但旧问题没有可匹配的对象级成功事实。
- 当前文件系统通用复核：
  - `1,909` 个问题目标已经不存在。
  - `86` 个问题目标已被当前隐藏目录、缓存目录或任务忽略规则排除。
  - 仅 `15` 个问题目标仍存在。
- 后续活动事实复核：
  - `15/15` 个授权问题所属任务均有更晚的成功活动运行。
  - `83/86` 个诊断问题所属任务有更晚的成功活动运行；剩余对象已不存在或已排除。
- 旧问题不是数据库损坏；现有生命周期只接受“同任务、同规范化路径、同操作族”的成功事件，缺少“目标已消失、路径已排除、任务已恢复、任务已停用”等当前状态收敛规则。

## 2. 修复目标

- 点击任意活动运行后，事件首屏查询使用现有索引，不再扫描 260 万条历史。
- 云端对象 token 仍存在时，不创建 cloud missing 墓碑，不产生虚假的待删活动。
- 问题中心保留真实仍可复现的问题，将已经不适用或已经恢复的历史问题转入“已解决”。
- 所有规则适用于任意升级用户，不依赖正式库中的任务 ID、路径或文件名。
- 不删除历史运行、事件、问题、出现记录和墓碑；只更新问题生命周期状态。

## 3. 活动事件查询

### 3.1 索引条件

- `run_id` 筛选改为原列直接 `IN`。
- `status` 输入在服务边界统一转为小写后，使用原列直接 `IN`。
- 模糊搜索继续允许 `coalesce/lower`，因为它本身不是索引等值查询。
- 保留总数、分页、时间范围和升降序接口契约。

### 3.2 验收

- 编译后的运行与状态筛选 SQL 不包含列函数包装。
- SQLite 查询计划对 `run_id` 使用 `SEARCH ... run_id=?`，不出现完整事件表扫描。
- 原有任务、运行、状态、搜索和时间组合筛选测试全部保持通过。

## 4. 云端缺失判定

下载扫描使用全部非忽略候选（包含重名候选）和文件夹建立本轮完整云端 token 集合，因此判定顺序调整为：

1. 同步映射的 `cloud_token` 存在于本轮 token 集合：对象仍存在，直接跳过缺失判断。
2. token 不存在，再比较目标路径集合。
3. token 与路径均无法证明对象存在时，才创建或刷新 cloud missing 墓碑。
4. 到期执行阶段继续保留 token 幂等复核，防止扫描与执行之间对象恢复。

该调整不改变真实云端删除、宽限期、严格删除、失败重试和本地回收目录逻辑。

## 5. 历史问题当前状态收敛

### 5.1 证据优先级

未解决问题按以下顺序验证：

1. 任务已删除或停用：`task_inactive`。
2. 授权问题之后存在同任务成功活动运行：`task_auth_recovered`。
3. 运行中断或系统诊断问题之后存在同任务成功活动运行：`later_run_succeeded`。
4. 对象路径已被当前同步忽略规则排除：`path_excluded`。
5. 同步根目录当前可用，且 upload、conversion 或 delete 对象当前已不存在：`target_absent_verified`。
6. 无上述证据：保持未解决。

对象级 upload/download 错误不能仅凭“任务后来成功”结案；仍优先使用现有精确恢复事实。下载目标不存在也不能视为下载成功。同步根目录不存在或暂时不可访问时不执行目标缺失结案，避免外接盘离线造成误判。

### 5.2 路径规则复用

- 同步运行与问题收敛共用同一个纯路径策略函数。
- 规则覆盖临时文件、隐藏目录、`__pycache__`、assets/attachments/figures、回收目录、云端 Markdown 镜像目录和任务自定义忽略子路径。
- 是否忽略隐藏/缓存路径继续读取现有全局配置。
- 文件存在性检查在线程中执行，避免阻塞 API 事件循环。

### 5.3 批次与重入

- 后台维护每批只读取固定数量未解决问题。
- 使用内存游标遍历问题集合；到达末尾后复位，避免不可解决的旧问题阻塞后续记录。
- 每个批次单事务更新；进程退出时未完成部分下次继续扫描。
- 当前状态收敛至多每 60 秒执行一次；同任务后续成功只从数据库返回最新一条，避免问题已稳定后持续加载运行历史。
- 新失败事件仍按现有指纹重新打开已解决问题。
- 不在页面 GET 请求中触发批量写入。

### 5.4 审计字段

- `state=resolved`
- `resolved_at`：证据发生时间或当前验证时间
- `last_good_at`：同上
- `resolution_verification`：上述稳定枚举
- 任务恢复证据写入 `resolved_by_run_id`
- 不删除 `latest_event_id`、`occurrence_count` 或原始 evidence

## 6. 页面行为

- 活动页不修改既有三档布局；修复数据返回速度和虚假活动源。
- 首次点击运行仍显示加载态；接口完成后显示真实事件或明确空态。
- 问题中心默认未解决数量随后台收敛下降；原记录可在“已解决”页签继续查看。
- 真正仍存在、没有恢复证据的对象错误继续显示，不以时间老旧为由自动解决。

  - 下载目标缺失不误结案；现存上传错误不误结案；新失败可重新打开。
